# 리니지 추출 방법론 (모듈 설계 v0.1)

> 전체 구조는 `data-lineage-saas-architecture.md`, 엔티티 스키마는
> `inventory-entity-schema.md`(3.7 그래프 스토어 파생 스키마, FLOWS_TO 엣지),
> 커넥터는 `connector-plugin-interface.md` 참고. 이 문서는 메인 문서의 4차
> 단계(데이터 리니지 연결)를 상세화한다.

## 1. 목적과 범위

FLOWS_TO 엣지(리니지 그래프의 핵심)를 실제로 어떻게 생성하는지를 정의한다.

**왜 "추출"인가**: 대부분의 시스템에는 "A가 B로 흐른다"는 정보가 그 자체로
저장돼 있지 않다. 이 관계는 SQL 코드, dbt 정의 파일, 실행 로그처럼 **다른
목적으로 만들어진 자료 안에 흔적으로만** 남아 있다. 리니지 그래프를 만든다는
건 이 흔적이 남는 곳을 찾아가 읽어내는(추출하는) 작업이고, 흔적이 남는 곳이
여러 군데라 아래 4가지 방법으로 나뉜다.

---

## 2. 추출 방법론 4가지

### 2.1 선언적 매니페스트 파싱 — 신뢰도 최상
dbt의 `manifest.json`처럼, 실행 엔진이 이미 "무엇에서 무엇으로 흐르는지"를
정의로 갖고 있는 경우. **추론이 아니라 정의를 그대로 읽는 것**이라 신뢰도가
가장 높다.

### 2.2 정적 SQL/쿼리 로그 파싱 — 신뢰도 중간, 커버리지 넓음
쿼리 로그나 저장 프로시저의 SQL을 AST 파싱해 `FROM`/`JOIN`/`INSERT INTO`
관계를 추출. 동적 SQL, ORM 생성 쿼리는 파싱이 틀리거나 빠질 수 있다.

### 2.3 런타임 트레이싱 — 신뢰도 상, 계측 비용 있음
Spark/Airflow 등에 OpenLineage 에이전트를 심어 실행 시점에 리니지 이벤트를
직접 emit. 정확하지만 계측 코드가 필요해 도입 장벽이 있다.

### 2.4 수동 매핑 — 흔적이 아예 없는 경우의 1급 입력 경로
위 세 가지는 모두 "어딘가에 흔적이 남아 있다"는 전제가 필요하다. 레거시
수기 배치, 폐기된 스크립트, 스캔 권한이 없는 시스템은 **흔적 자체가 존재하지
않아** 자동 추출이 원천적으로 불가능하다. 이 공백이 구조적으로 클 수 있으므로,
수동 매핑은 "안 되면 쓰는 폴백"이 아니라 **1급 입력 경로**로 설계한다 — 상세는
3장.

**MVP 우선순위**: 2.1(dbt) → 2.2(쿼리 로그) → 2.4(수동, 처음부터 제공) →
2.3(런타임 트레이싱, 2단계 이후).

---

## 3. 수동 매핑 설계 (커버리지 공백에 대한 1급 대응)

### 3.1 등록된 오브젝트 간 연결
검색으로 출발/도착 Object를 골라 엣지를 생성하는 기본 형태. 사람이 직접
등록한 엣지는 confidence를 확정값으로 두고, 5장의 검수 큐를 거치지 않는다.

### 3.2 미등록 대상을 위한 외부 엔드포인트 (ExternalEndpoint)
연결의 상대편이 아예 스캔 대상이 아닌 경우(수기 엑셀 보고서, 스캔 권한이
없는 레거시 시스템)가 흔하다. 이럴 때 억지로 Object를 만들 필요 없이, 자유
텍스트 설명("재무팀 월간 수기 집계")만으로 연결의 한쪽 끝을 표현하는 경량
노드 타입을 둔다. 그래프 순회의 실질 대상이라기보다, "이 데이터가 여기까지
나갔다"는 걸 사람이 확인할 수 있게 하는 표식이다.
→ `inventory-entity-schema.md`의 그래프 스토어 파생 스키마(7장)에 이 노드
타입을 추가로 반영해야 한다 (열린 항목).

### 3.3 일괄 등록 (스프레드시트 업로드)
많은 팀이 이미 "이 테이블은 저 리포트로 간다" 같은 관계를 자체 스프레드시트로
관리한다. 하나씩 폼으로 입력하게 하지 않고, `source_object, target_object,
description` 템플릿을 업로드해 한 번에 여러 엣지를 등록할 수 있게 한다 —
이미 갖고 있는 기록을 다시 타이핑하게 만들지 않는 게 채택률에 중요하다.

### 3.4 한계 인정
수동 매핑도 결국 사람이 기억하고 입력해야 가능하다. 아무도 모르거나 아무도
입력하지 않은 연결은 여전히 그래프에 나타나지 않는다. 이건 기술로 완전히
해결되지 않는 구조적 한계이므로, 카탈로그/리포트에 "이 그래프는 알려진
연결만 반영하며 완전하지 않을 수 있다"는 걸 명시적으로 표시해야 한다 —
불완전한 그래프를 완전한 것처럼 보여주는 게 가장 위험하다(앞선 논의: 자동
추출 과신의 위험과 같은 이유).

---

## 4. MVP 스코프: 테이블(오브젝트) 레벨만

컬럼 레벨 리니지는 SQL AST에서 JOIN/CASE/서브쿼리를 추적해야 해서 난이도가
훨씬 높다. MVP는 오브젝트(테이블/토픽) 단위로만 FLOWS_TO 엣지를 만들고,
컬럼 레벨은 2단계 이후로 미룬다.

---

## 5. 엔티티 매칭 (Entity Resolution)

파싱 결과는 "스키마.테이블명" 같은 문자열이고, 그래프 노드는 등록된 Object
row다.

- 매칭 키: `(source_id, object_name)` — 인벤토리 스키마 3.3의 `UNIQUE(source_id,
  name)` 제약과 동일한 키를 쓴다.
- 여러 소스를 넘나드는 파이프라인(DB → Kafka → DW)은 소스 타입별 커넥션
  식별자로 1차 후보를 좁힌 뒤 이름으로 확정한다.
- **매칭 실패 시**: 엣지를 버리지 않고 `unresolved_reference`로 표시해
  거버넌스 리포트에 노출한다 — "등록 안 된 소스가 파이프라인에 연결돼
  있다"는 신호이자, UnclaimedAsset 탐지(인벤토리 스키마 3.8)와 다른 각도로
  그레이 영역을 잡아내는 보조 수단이 된다.

---

## 6. 신뢰도 스코어링 및 검수 워크플로우

| 방법 | 기본 confidence |
|---|---|
| 2.1 매니페스트 파싱 | 높음 |
| 2.2 SQL 파싱 | 파싱 성공 여부·복잡도에 따라 가변 |
| 2.3 런타임 트레이싱 | 높음 |
| 2.4 수동 매핑 | 확정값 (검수 불필요) |

`confidence`가 임계값 미만인 엣지는 `pending_review` 상태로 큐에 쌓이고
담당자가 승인/반려한다(`reviewed_by`). 승인 전에는 블래스트 레이디어스 등
의사결정용 리포트에서 기본 제외하거나 "검증 안 됨" 표시를 단다.

---

## 7. 엣지 버저닝

Object/Field와 마찬가지로 FLOWS_TO 엣지도 `valid_from`/`valid_to`를 가진
SCD Type 2 방식으로 관리한다. 파이프라인 정의가 바뀌면 기존 엣지는
`valid_to`를 채우고 새 엣지를 추가한다.

---

## 8. 오브젝트 단위 게이팅 원칙의 적용 여부

`onboarding-orchestration.md`의 오브젝트 단위 게이팅은 리니지 추출에는 그대로
적용하지 않는다. 리니지 추출은 파이프라인 정의(dbt 프로젝트, SQL 파일) 단위로
실행되는 게 자연스럽고, 이 단위가 여러 오브젝트에 걸친 엣지를 한 번에
만들어낸다. 대신:

- 파이프라인 정의 단위로 증분 추출(변경된 모델/SQL 파일만 재파싱)
- 추출된 엣지가 카탈로그에 반영되는 시점은 오브젝트 단위 게이팅을 그대로 따름
