# 온보딩/스캔 오케스트레이션 모듈 설계 (v0.1)

> 전체 구조는 `data-lineage-saas-architecture.md`, 엔티티 스키마는
> `inventory-entity-schema.md` 참고. 이 문서는 메인 문서의 "스캔 오케스트레이터"
> (4.2)를 상세화한다.

## 1. 목적과 범위

4단계 순차 온보딩(도메인 범위 → 유형 설정 → 인벤토리 → 리니지)이 실제로 어떻게
진행되는지 — 잡 상태 모델, 스테이지 게이팅 규칙, 진행률 집계, 재시도/재개,
증분 재스캔 — 를 정의한다. **가장 큰 목표는 온보딩 체감 시간 단축**이다.

---

## 2. 문제 진단: 왜 느려지는가

1. **도메인 단위 게이팅** — "도메인 전체가 1차를 끝내야 2차 시작" 같은 규칙이면
   대형 도메인(테이블 수만 개)은 첫 결과가 나오기까지 몇 시간이 걸린다.
2. **일괄 무거운 샘플링** — 모든 컬럼에 동일한 크기의 샘플을 뽑아 분류하면,
   컬럼 수에 비례해 분류 워커 부하가 선형으로 증가한다.
3. **순서 없는 처리** — 큰 테이블과 작은 테이블을 무작위 순서로 처리하면,
   사용자가 초기 가치를 느끼기까지의 시간이 운에 좌우된다.
4. **전체 재스캔** — 변경 감지 없이 매번 전체를 다시 스캔하면, 온보딩 이후
   반복 스캔도 계속 느리다.
5. **하나의 실패가 전체를 막음** — 격리되지 않은 재시도 로직은 문제 있는
   오브젝트 하나가 전체 배치 완료를 지연시킨다.
6. **도메인 구성 자체가 점진적** — 담당자/TF가 며칠에 걸쳐 소스를 하나씩
   검토·승인하는 게 현실이라, "도메인이 확정되는 시점"이 애초에 없다.
7. **등록되지 않은 자산의 존재** — TF가 등록한 소스 목록과 실제 회사가 보유한
   DB/인프라 목록 사이에 간극이 있을 수 있다 (그레이 영역).

1-5는 처리 속도/부하 문제, 6-7은 "도메인 범위 자체가 불완전하거나 유동적"이라는
문제라 3~4장에서 별도로 다룬다.

## 3. 소스 승인 상태 모델 (점진적 도메인 구성 대응)

Source는 등록되는 즉시 스캔 대상이 되는 게 아니라, TF의 논의 과정을 담는
상태를 거친다.

```
proposed (제안됨) → approved (승인됨) → active (스캔 개시)
                                     └→ excluded (제외됨)
```

- `proposed`: TF가 후보로 올려둔 상태. **스캔이 트리거되지 않는다.**
- `approved`: 승인 완료. 이 시점에 스캔 오케스트레이터 큐에 들어간다.
- `active`: 스캔 진행 중/완료.
- `excluded`: 논의 후 제외. 이력은 남기고 스캔 대상에서 뺀다.

**변경 이력 로그**: `source_status_log(source_id, from_status, to_status,
changed_by, changed_at, note)` — 누가 언제 왜 상태를 바꿨는지 기록.

**도메인에는 "완료" 상태가 없다.** 도메인 홈 화면은 항상 열려 있고, TF는
언제든 돌아와 소스를 더 제안/승인/제외할 수 있다.

---

## 4. 미할당 자산 탐지 (그레이 영역 대응)

TF가 등록한 Source 목록에만 의존하면, "아무 도메인에도 속하지 않은 DB"를
놓칠 수 있다. 이건 온보딩 흐름 안에서 자연스럽게 풀리지 않아 별도 대조
(reconciliation) 메커니즘을 둔다.

- **인프라 레벨 스캔(베스트 에포트)**: Domain/Source 등록과 무관하게, 클라우드
  계정 API(AWS Resource Groups, GCP Asset Inventory, Azure Resource Graph 등)로
  "이 계정에 존재하는 모든 DB/스토리지 인스턴스 목록"을 가져온다. 이건 사람이
  등록했는지와 무관하게 도는 인프라 관점의 원장(ledger)이다.
- **대조**: 이 목록을 등록된 Source의 connection 정보(host/ARN 등)와
  자동 대조해, 매칭 안 되는 자산은 `UnclaimedAsset` 풀에 쌓인다
  (`inventory-entity-schema.md` 3.8 참고).
- **트리아지**: 미할당 자산은 스캔/분류 파이프라인에 자동으로 들어가지 않고,
  거버넌스 리포트로만 노출된다. 담당자가 주기적으로 "기존 도메인에 편입 /
  새 도메인 필요 / 무시(샌드박스 등)"로 분류한다.
- **한계**: 클라우드 계정 API 접근 권한이 없으면 이 기능은 비활성화된다.
  없어도 나머지 파이프라인은 정상 동작해야 한다 — 이 기능은 필수 경로가
  아니라 보강 장치다.

## 5. 핵심 원칙: 오브젝트 단위 게이팅

스테이지 전환은 **오브젝트(테이블/토픽/파일) 단위**로 독립적으로 일어난다.
도메인이나 소스 전체가 한 스테이지를 끝내길 기다리지 않는다.

```
오브젝트 A: [디스커버리 완료] → [구조 추출] → [분류/프로파일링] → [카탈로그 등록]
오브젝트 B: [디스커버리 완료] → [구조 추출] → [분류/프로파일링] → [카탈로그 등록]
오브젝트 C: [디스커버리 중............]
```

오브젝트 A가 먼저 끝나면 카탈로그에 바로 노출된다 — 도메인 전체가 끝날 때까지
기다리지 않는다. 도메인/소스 단위 "진행률"은 이 개별 오브젝트 상태를 집계한
결과일 뿐, 게이팅의 기준이 아니다.

---

## 6. Object 레벨 스코프 필터링 (규칙 기반 + 예외 처리)

오브젝트 하나하나를 사람이 확인해서 다음 단계로 보낼지 정하는 방식은 온보딩
체감 시간을 줄이려는 목표와 충돌한다 (테이블 수백 개를 수동으로 고르는 건
새로운 병목이다). 대신 기본값은 자동 진행이고, 범위를 좁히고 싶을 때만
규칙을 건다.

```
기본값: 발견된 오브젝트는 전부 자동으로 다음 단계(구조 추출→분류/프로파일링) 진행
선택적 규칙: 이름 패턴(*_tmp, *_bak), 태그(dev/staging), 오너 팀 등 조건에
            맞으면 자동으로 제외 (Object.scan_status = excluded_by_rule)
```

**규칙으로 안 걸리는 예외 케이스는 반드시 있다.** 이름 패턴이나 태그로 안
잡히는 애매한 테이블(예: 이름은 정상인데 실제로는 임시 용도)이 있을 수
있으므로, 규칙 기반 자동 제외 위에 **수동 예외 처리 목록**을 둔다 — 카탈로그
화면에서 개별 오브젝트를 "제외" 처리할 수 있고(`scan_status =
excluded_manual`), 이건 규칙을 새로 만들 것도 없이 건별로 즉시 적용된다.
즉 규칙은 대량 케이스를 처리하고, 수동 처리는 규칙이 놓치는 소수 예외를
보완하는 안전판이다.

## 7. 잡 상태 모델

| 필드 | 설명 |
|---|---|
| job_id (PK) | |
| entity_type | OBJECT / FIELD — 어떤 엔티티에 대한 잡인지 |
| entity_id (FK) | Object.object_id 또는 Field.field_id |
| stage | discovery / structure_extract / classify / profile / catalog |
| status | pending / running / done / failed |
| retry_count | |
| last_error | nullable |
| started_at / completed_at | |
| next_retry_at | 지수 백오프 스케줄링용 |

**인덱스**: `(entity_id, stage)` UNIQUE — 엔티티당 스테이지별 잡은 하나만 존재.
`(status, next_retry_at)` — 재시도 스케줄러가 폴링하는 인덱스.
`(stage, status)` — 도메인/소스 진행률 집계 쿼리용.

`excluded_by_rule`/`excluded_manual` 상태인 Object는 애초에 잡이 생성되지
않는다 — 6장의 필터링은 잡 큐에 들어가기 전 단계에서 걸러진다.

---

## 8. 스테이지 게이팅 규칙

- 오브젝트는 `discovery → structure_extract → {classify, profile} → catalog` 순서로
  전진한다.
- `classify`와 `profile`은 서로 의존하지 않으므로 병렬 실행. `catalog` 진입은
  둘 다 `done`이어야 함 (또는 타임아웃 후 부분 상태로 진입 — 9장 참고).
- 한 오브젝트의 진행이 다른 오브젝트의 게이팅에 영향을 주지 않는다 — 오브젝트
  간에는 게이팅이 없다.

---

## 9. 재시도 / 격리

- 실패한 잡은 지수 백오프(`next_retry_at`)로 재시도, 최대 재시도 횟수 초과 시
  `failed` 상태로 고정하고 데드레터 큐에 기록.
- **격리 원칙**: 오브젝트 하나의 재시도/실패는 다른 오브젝트의 처리를 막지
  않는다. 워커 풀은 오브젝트 단위로 잡을 꺼내 쓰므로, 느린 오브젝트 하나가
  큐 전체를 블로킹하지 않도록 오브젝트별 타임아웃을 둔다.
- 타임아웃 초과 시 `classify`/`profile` 중 하나만 실패해도, 카탈로그에는
  "부분 완료" 상태로 노출한다 (예: 구조 정보는 있지만 분류 결과는 아직 없음
  — `eligible_for_training`을 `pending_review`로 표시). 완전한 결과를
  기다리다 카탈로그 노출 자체가 지연되는 것보다, 있는 정보라도 먼저 보여주는
  쪽이 온보딩 체감 시간에 유리하다.

---

## 10. 진행률 집계

도메인/소스 단위 진행률은 잡 상태 테이블에 대한 집계 쿼리로 계산한다.

```
진행률(스테이지 N) = count(entity WHERE stage >= N AND status = done)
                    / count(entity WHERE domain_id = X AND scan_status NOT IN
                      ('excluded_by_rule', 'excluded_manual'))
```

이 집계는 매 이벤트마다 재계산하지 않고, 진행 이벤트 버스로 들어오는 잡 완료
이벤트를 받을 때마다 도메인별 카운터를 증분 갱신한다.

이 수치는 "도메인 전체 대비 %"가 아니라 **"현재 승인된 소스, 필터링 이후
남은 오브젝트 기준"** 임을 분명히 한다 — 3장의 소스 승인 상태와 6장의 스코프
필터링 둘 다 분모에서 이미 반영된 값이다.

---

## 11. 누적/델타 리포팅 (소스가 하나씩 추가되는 상황 대응)

도메인은 "완료"가 없고 소스가 하나씩 승인되며 자란다. 이 구조에서 "전체
인벤토리가 다 만들어져야 가치가 나온다"는 인상을 주면 안 된다.

- **소스 단위 델타 리포트**: 소스 하나의 스캔이 끝날 때마다 자동으로 짧은
  요약을 발행한다 — "이 소스에서 테이블 42개 확인, 그 중 PII 포함 6개, 위험도
  상위 3개는 …".
- **누적 뷰는 절대값 + 추세로 표시, 완료율(%)로 표시하지 않는다**: 분모(전체
  소스 수)가 확정되지 않았으므로 "62% 완료" 같은 수치는 오해를 낳는다.
- **도메인 성숙도 라벨(선택적)**: 완료율 대신 "탐색 중 → 부분 커버리지 확보 →
  안정적 운영" 같은 정성적 단계 라벨을 쓸 수 있다.

---

## 12. 스케줄링 우선순위 (체감 속도 개선)

기본적으로는 FIFO가 아니라 아래 우선순위로 큐를 정렬한다.

1. `criticality_tier`가 높은 오브젝트 우선 (Source 등록 시 입력된 값)
2. 작은 오브젝트(예상 row_count/메시지량 낮은 순) 우선
3. 나머지는 발견 순서(FIFO)

---

## 13. 적응형 샘플링 (분류/프로파일링 부하 절감)

모든 필드에 동일한 크기의 샘플을 쓰지 않는다.
- 1차 패스: 소규모 샘플(예: 100행)로 분류/프로파일링 실행
- 신뢰도(`confidence_score`)가 임계값 미만인 필드만 더 큰 샘플로 재실행

---

## 14. 증분 재스캔

- Object 등록/갱신 시 스키마 핑거프린트(컬럼 목록 + 타입의 해시)를 저장
- 재스캔 시 현재 스키마의 해시와 비교해 변경 없으면 스킵, `last_scanned_at`만 갱신
- 변경 감지 시에만 해당 오브젝트를 처음부터 다시 큐에 넣음
- 도메인 범위가 넓어질 때도 동일한 메커니즘으로, 새로 추가된 오브젝트만
  큐에 들어가고 기존 오브젝트는 건드리지 않음
