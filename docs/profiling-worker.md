# 프로파일링 워커 상세 설계 (모듈 설계 v0.1)

> 전체 구조는 `data-lineage-saas-architecture.md`(4.4 프로파일링 워커),
> 엔티티 스키마는 `inventory-entity-schema.md`(3.5 Profiling), 커넥터 안전
> 원칙은 `connector-plugin-interface.md`(2장), 분류 워커와의 관계는
> `classification-worker.md` 참고.

## 1. 목적과 범위

산출할 품질/신선도 지표의 1차 범위, 계산 방법(안전 원칙 적용), 분류 워커와의
실행 관계를 정의한다.

---

## 2. 산출 지표 (1차 범위)

| 지표 | 설명 |
|---|---|
| null_ratio | 결측치 비율 |
| cardinality | 고유값 개수(또는 근사치) |
| distribution_summary | 상위 값/히스토그램 요약 (3장의 마스킹 정책 적용) |

**신선도는 Field가 아니라 Object 레벨 지표를 재사용한다** — `last_modified_at`은
이미 Object에 있고(인벤토리 스키마 3.3), Field마다 별도로 둘 필요가 없다.

**2단계로 미루는 것**: 분포 드리프트 감지(과거 프로파일링 결과와 비교해 분포가
급격히 바뀌었는지), 데이터 타입 일관성 검사(선언된 타입과 실제 값의 불일치
탐지)는 1차 범위에서 제외한다.

---

## 3. 계산 방법 — 안전 원칙 우선순위

`connector-plugin-interface.md` 2.2의 "카탈로그 통계 우선" 원칙을 그대로
따른다.

1. **엔진 통계 우선**: PostgreSQL `pg_stats`의 `null_frac`, `n_distinct` 같은
   이미 계산된 통계가 있으면 그대로 가져온다 — 데이터를 읽지 않으므로 무해.
2. **통계가 없으면 안전한 샘플링**: `connector-plugin-interface.md` 2.2의
   샘플링 방식(`TABLESAMPLE`, PK 기반 해시 모듈로)으로 근사치를 계산.
3. **분류 워커와 달리 반복 에스컬레이션을 하지 않는다** — 분류는 "애매한
   경우"가 있어 신뢰도가 낮으면 샘플을 키우는 게 의미 있지만, 프로파일링은
   통계적 근사라 오차 범위를 명시하는 게 샘플을 반복해서 키우는 것보다
   합리적이다. `profiling_summary`에 `estimation_method: exact | sampled`
   플래그를 남겨, 카탈로그 화면에서 "정확한 값"과 "추정치"를 구분해 보여준다.

### 3.1 민감 필드의 distribution_summary 마스킹 정책
`distribution_summary`(상위 값 목록)는 그 자체로 실제 값을 노출할 위험이
있다. 프로파일링 워커는 결과를 저장하기 직전, 해당 Field의 최신
Classification 결과를 조회한다 — PII로 판정된 필드는 상위 값 목록 대신
분포의 "모양"(예: 히스토그램 버킷 개수, 최빈값 비율 같은 값 자체를 감추는
요약)만 저장한다. 민감하지 않은 필드만 실제 상위 값을 저장한다.

이건 3.5(인벤토리 스키마)에서 "분류와 프로파일링은 FK 의존 없이 병렬 실행"
이라고 정의한 것과 완전히 독립은 아니라는 뜻이다 — **FK 의존은 없지만,
저장 직전에 분류 결과를 참조하는 정책적 의존이 있다.** 분류가 아직
안 끝났다면(=Classification row가 없다면) 안전한 쪽으로 기본값을 잡아
마스킹된 형태로 저장하고, 이후 분류가 완료되면 재평가하지 않는다(불필요한
재작업 방지 — 카탈로그 화면에는 "분류 대기 중이었을 때 저장된 요약"이라는
표시만 남긴다).

## 5. 카탈로그/검색 노출

검색 결과에 `null_ratio`는 이미 `inventory-entity-schema.md` 6장의 검색
인덱스 문서 스키마에 포함돼 있다. `cardinality`는 아직 빠져 있어 추가가
필요하다 (열린 항목).
