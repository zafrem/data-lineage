# 데이터 리니지 제품 아키텍처 (v0.1 초안)

## 1. 제품 개요

OpenMetadata류의 데이터 리니지 제품. 지정된 데이터를 스캔해 데이터 유형을 파악하고,
이를 기반으로 여러 시작점(source)에서 출발하는 데이터 흐름(리니지)을 구성한다.

**1차 타겟 사용자: 데이터 사이언스/ML 엔지니어.** 이들의 "검색 → 신뢰성 확인 →
추출/사용" 워크플로우를 매일 쓰는 기반으로 만드는 것이 목표다. 데이터 엔지니어/
보안 거버넌스는 2차 사용자로, 같은 파이프라인의 부산물(리스크 히트맵, 거버넌스 갭
리포트 등)을 소비한다. 경영진용 요약(비용 절감/리스크 예산 근거)은 이 두 사용자층의
활동에서 파생되는 3차 산출물로 취급한다.

설치는 한 번에 끝나는 빅뱅 방식이 아니라, 아래 4단계로 순차 진행되며
**모든 단계가 끝나기 전에도 UI로 중간 진행 상황을 확인할 수 있어야 한다.**

| 단계 | 내용 |
|---|---|
| 1차 | 도메인 범위 설정 + **데이터 소스 객체 등록** (DB, Kafka, DW 등 소스 인스턴스와 유형·특성 등록) |
| 2차 | 데이터 유형 설정 (구조적 타입 + 시맨틱/민감 유형 분류 + **프로파일링**) |
| 3차 | 데이터 인벤토리 생성 (카탈로그화) |
| 4차 | 데이터 리니지 연결 (테이블/컬럼 간 흐름 그래프 구성) |

향후 확장 기능(우선순위는 인벤토리 이후):
- 태깅 및 거버넌스 워크플로우
- 비식별화 기반 ML 학습 데이터 추출 기능
- 임팩트 분석 / 변경 알림

## 2. 핵심 설계 원칙

1. **단계별 독립 산출물** — 각 단계는 그 자체로 리포트/가치를 만들어야 한다. 4단계가
   모두 끝나야 가치가 생기는 구조는 지양한다.
2. **엔진은 하나, 배포 토폴로지만 분리** — 분류/탐색 엔진, 인벤토리 스키마, UI 코드는
   동일 산출물(컨테이너 이미지)로 만들고, 어디서 실행되는지만 고객 세그먼트별로 달리한다.
3. **샘플 데이터는 휘발성** — 유형 분류를 위해 읽은 실제 데이터(샘플)는 판정이 끝나면
   즉시 폐기하고, 판정 결과(유형 + 신뢰도 점수)만 영속 저장한다.
4. **아웃바운드 전용 연결** — 벤더 인프라가 고객 네트워크로 먼저 접속하는 경로는 없다.
   고객 측 컴포넌트가 항상 먼저 연결을 연다.

## 3. 데이터 소스 객체 모델

테이블/컬럼만 1급 엔티티로 다루면 "이 오브젝트가 어느 소스에서 왔는지, 그 소스의
특성(환경, 오너, 갱신 주기)이 무엇인지"를 표현할 자리가 없어진다. 소스 자체를
별도 계층으로 등록해야 한다.

```
Domain (도메인 범위)
  └─ Source (소스 객체: 이 PostgreSQL 인스턴스, 이 Kafka 클러스터, 이 Snowflake DW)
       └─ Object (소스 내 단위: 테이블 / 토픽 / 파일-버킷 경로)
            └─ Field (컬럼 / 메시지 필드 / 파일 스키마 필드)
```

1차 단계는 두 하위 단계로 구성된다.
- **1a. 도메인 범위**: 스캔할 팀/사업영역 지정
- **1b. 소스 객체 등록**: 고정된 소스 타입 taxonomy에서 유형을 선택하고, 연결 정보 +
  소스 단위 특성을 등록. 이 등록이 2차보다 먼저 끝나야, 분류 워커가 오브젝트 종류별로
  다른 추출 로직(테이블 vs 토픽 vs 파일)을 분기할 수 있다.

소스 타입별로 등록 시 요구되는 특성이 다르다:

| 소스 타입 | 등록 시 특성 예시 |
|---|---|
| RDB | 엔진 종류/버전, 운영·개발 환경 |
| DW | 웨어하우스 종류, 리프레시 주기 |
| Kafka/스트리밍 | 스키마 레지스트리 연동 여부, 직렬화 포맷(Avro/Protobuf/JSON) |
| Object Storage | 파일 포맷(Parquet/CSV/JSON), 파티셔닝 규칙 |

이 소스 메타데이터는 3차 인벤토리에서 오브젝트의 상위 계층으로 유지되어, "운영 DB에
있는 테이블만 보기" 같은 소스 단위 필터링/검색을 가능하게 한다.

**모델 아티팩트 노드 (데이터 사이언스 사용자 대응)**: 4차 리니지 그래프는 데이터→데이터
흐름 외에, 데이터 사이언스 사용자를 위해 **Model** 노드 타입도 포함한다. "이 모델이
어떤 데이터셋 버전으로 학습됐는가"를 역방향으로 추적할 수 있어야, 특정 데이터셋에
문제가 발견됐을 때 영향받는 모델 목록과 재학습 필요 여부를 답할 수 있다.

## 4. 컴포넌트 아키텍처

```
[커넥터/스캔 에이전트] → [스캔 오케스트레이터] → [구조 추출 워커] ─┐
                                              ├→ [분류 워커 (entiscope 연동)] ─┤
                                              └→ [프로파일링 워커] ──────────┤
                                                                              ↓
                                                                    [인벤토리 스토어]
                                                                    (메타데이터 + 검색 색인)
                     구조 추출/분류/프로파일링 워커 완료 이벤트
                                ↓
                       [진행 이벤트 버스] → [UI 진행률 화면]
```

### 4.1 커넥터/스캔 에이전트
- 소스 유형별(RDB, DW, Object Storage, 스트리밍) 플러그인 구조
- 두 가지만 책임: (1) 메타데이터 수집 (카탈로그/information_schema, 스키마 레지스트리 등
  소스 타입에 맞는 방식), (2) 분류용 소량 샘플링
- 1b(소스 객체 등록) 단계에서 등록된 소스 타입에 따라 어떤 추출 로직을 태울지 결정
- 자격증명은 별도 Vault/KMS에서 주입 — 커넥터 자체에 저장하지 않음

### 4.2 스캔 오케스트레이터
- 도메인 스캔(가벼움) / 타입 분류(무거움, CPU·GPU 바운드) / 인벤토리 적재(I/O 바운드)를
  별도 워커 풀·큐로 분리 — 무거운 작업이 가벼운 작업을 막지 않도록
- 테이블 단위로 잡을 쪼개 스테이지별 진행 상태를 추적하는 잡 상태 저장소 보유
  (재시도/재개(resume)를 위해 필수)

### 4.3 구조 추출 워커 / 분류 워커
- 구조 추출: 오브젝트 타입별 구조적 메타데이터 조회 (테이블의 SQL 타입, 토픽의 스키마 등)
- 분류: entiscope 기반 시맨틱 유형(이메일, 전화번호 등) 판정 + 신뢰도 점수 산출
- 분류 워커 → 인벤토리로 넘어가는 것은 **판정 결과뿐**, 샘플 원본은 이 경로를 타지 않음

### 4.4 프로파일링 워커 (신규 — 데이터 사이언스 사용자 대응)
- 분류 워커와 별개로, 결측치 비율·카디널리티·분포·마지막 갱신 시점 등 **품질/신선도
  지표**를 산출
- 데이터 사이언스 사용자가 "이 데이터를 써도 되는가"를 판단하는 데 분류 결과(PII 여부)
  만큼 중요하게 쓰는 지표
- 분류 워커와 마찬가지로 판정 결과만 인벤토리로 전달, 샘플 원본은 폐기

### 4.5 인벤토리 스토어
- 메타데이터 본체(관계형 DB, Domain → Source → Object → Field 계층 + 버전 이력)
- 검색/카탈로그 조회용 별도 검색 인덱스
- 검색 결과 단위로 **"학습 가능 여부" 상태 필드** 보유 (예: 비식별화 완료 / 원본 PII
  포함·승인 필요) — 데이터 사이언스 사용자가 카탈로그 검색 시 바로 판단 가능해야 함
- 4차 리니지 단계의 그래프 노드 기반이 되는 스키마

### 4.6 진행 이벤트 버스 / UI
- 각 워커가 엔티티(테이블/컬럼) 단위 작업을 완료할 때마다 이벤트 발행
- UI는 이 스트림을 구독(SSE/웹소켓)해 전체 배치 완료 없이 실시간 진행률 표시
- 스테이지 완료 시 요약 리포트를 자동 발행하는 상위 이벤트도 함께 설계

## 5. 배포 토폴로지 (세그먼트별)

동일 엔진을 두 가지 배포 모드로 지원한다.

| 항목 | 하이브리드 (소규모) | 완전 온프레미스 (대규모) |
|---|---|---|
| 컨트롤 플레인(UI, 리포팅) | 벤더 클라우드 | 고객 내부 |
| 데이터 플레인(스캔 에이전트, 분류 엔진) | 고객 내부 | 고객 내부 |
| 검색 인덱스 / 인벤토리 | 고객 내부 | 고객 내부 |
| 네트워크 연결 방향 | 에이전트 → 클라우드 아웃바운드만 | 에어갭 가능, 자동 연결 없음 |
| 업데이트 수신 | 자동 pull | 서명된 패키지 수동 반입 가능 |
| 온보딩 | 셀프서비스 | 영업/전문서비스 지원 |
| 과금 | 구독 + 사용량 기반 | 라이선스/계약 협상 |

**공통 원칙**: 실제 고객 데이터(메타데이터, 검색 인덱스, 분류 결과)는 두 모드 모두
고객 내부에 남는다. 클라우드 쪽에 있는 것은 UI 프레젠테이션 계층과 업데이트 배포
채널뿐이며, 이 둘은 고객의 실제 데이터를 포함하지 않는다.

업데이트는 성격이 다른 세 가지를 독립적으로 버전 관리한다:
1. 분류 룰/패턴 업데이트
2. ML 모델 가중치 업데이트
3. 엔진 자체(커넥터, 코어 로직) 업데이트

## 6. 단계별 리포팅 (독립 산출물)

| 단계 | 리포트 |
|---|---|
| 1차 도메인 범위 | 자산 발견 리포트 — 소스/테이블 규모, 미문서화 자산 카운트 |
| 2차 데이터 유형 | 민감정보 노출 히트맵 — 테이블×유형 매트릭스, 리스크 스코어 랭킹 |
| 3차 인벤토리 | 카탈로그(즉시 사용 가능) + 오너 미배정/저품질 테이블 거버넌스 갭 리포트 |
| 4차 리니지 | 커버리지율 지표 + 부분 임팩트 분석 (완성 전에도 데모 가능) |
| 운영 중(지속) | **사용량/재사용 리포트** — 검색·추출 빈도 기반 데이터 자산 활용도. 경영진의 투자 우선순위 결정에 근거로 쓰일 수 있는 유일하게 검증 가능한 지표 |
